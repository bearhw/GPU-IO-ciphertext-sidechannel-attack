────────────────────────────────────────────────────────────────────────────────
0. 우리가 하려는 것 (한 문장 요약)
────────────────────────────────────────────────────────────────────────────────

  "Chest pain" 같은 알려진 문구가 토큰화됐을 때의 ciphertext(암호문)를
  미리 캡처해서 사전(딕셔너리)에 저장해두고, 나중에 실제 추론 중인
  게스트 메모리의 ciphertext와 비교해서 "이 위치에 어떤 문구가 있었는지"
  알아내는 게 최종 목표. 이 문서는 그 "미리 캡처하는" 과정(= 딕셔너리 빌드)이
  어떻게 동작하는지를 다룬다.

  핵심 전제 (SEV-SNP AES-XEX):
    같은 평문(plaintext) + 같은 물리주소(GPA) = 항상 같은 암호문(ciphertext)

  그래서: "Chest pain"의 토큰 ID를 알려진 GPA에 놓고 암호문을 한 번 찍어두면,
  나중에 실제 indication이 그 GPA(정확히는 그 오프셋)에 왔을 때 암호문만
  비교해도 "Chest pain"이었는지 알 수 있다.

────────────────────────────────────────────────────────────────────────────────
1. 왜 이렇게 복잡한가? — 문제는 "내가 원하는 GPA에 원하는 토큰을 어떻게 놓냐"
────────────────────────────────────────────────────────────────────────────────

  우리는 호스트에서 게스트 커널을 통해 ICMP 패킷을 하나 보낸다. 그 패킷의
  내용(payload)이 특정 토큰 ID들이 되도록 우리가 원하는 대로 채울 수 있다.
  하지만 그 패킷이 게스트 메모리의 "어느 물리 페이지, 어느 오프셋에" 저장될지는
  우리가 직접 지정할 수 없다 — 게스트 커널의 내부 버퍼 할당 상태에 달려있다.

  그래서 딕셔너리 빌드는 사실 이런 문제를 푸는 것이다:

    "내용은 내가 정할 수 있지만 위치는 못 정하는 상황에서,
     어떻게든 '이 페이지 전체가 내가 원하는 토큰 패턴으로만 꽉 찬' 상태를
     만들어내고, 그 페이지가 정확히 어느 물리주소인지 알아내라."

────────────────────────────────────────────────────────────────────────────────
2. 큰 페이로드로 "꽉 찬 페이지" 보장하기
────────────────────────────────────────────────────────────────────────────────

  아이디어: 토큰 시퀀스(예: "Short of breath" = 3개 토큰 = 24바이트)를
  아주 길게(12288바이트 = 4KB 페이지 3개 분량, ICMP_PAYLOAD_MIN) 반복해서
  채운 페이로드를 하나의 ICMP 패킷으로 보낸다.

    [token][token][token][token][token]... (24바이트 패턴이 12288바이트까지 반복)

  이 데이터가 게스트 메모리 어디에 저장되든, 시작 위치가 페이지 경계에서
  얼마나 어긋나 있든 상관없이 — 데이터가 충분히 길기 때문에(2×4096-1=8191바이트
  이상이면 수학적으로 보장됨) 중간의 어느 한 페이지는 반드시 처음부터 끝까지
  전부 우리 반복 패턴으로 채워진다.

  비유:
    "ABC"라는 3글자가 끝없이 반복되는 무한히 긴 종이 테이프
    (ABCABCABCABCABC...)를 상자 여러 개에 나눠 담는다고 하자.
    각 상자가 딱 정확히 "ABC"로 시작하리라는 보장은 없다(중간에 잘릴 수 있음:
    예를 들어 "BCA"로 시작하는 상자가 있을 수 있음). 하지만 테이프가 충분히
    길면, 앞/뒤 상자를 빼고 "중간 상자들"은 100% "ABC" 반복 패턴으로만
    채워져 있다는 건 확실하다 — 그 상자 안에 다른 내용이 섞일 여지가 없다.

  이 "중간에 있는, 100% 우리 패턴으로 찬 페이지"를 찾아서 쓰는 것 —
  이게 딕셔너리 빌드의 1단계다.

────────────────────────────────────────────────────────────────────────────────
3. 패킷은 여러 조각(fragment)으로 쪼개져서 도착한다
────────────────────────────────────────────────────────────────────────────────

  12288바이트짜리 패킷을 보내면, 게스트 커널이 이걸 하나의 연속된 메모리
  덩어리에 통째로 담는 게 아니라, 물리적으로 떨어진 여러 조각(frag[0],
  frag[1], frag[2]...)으로 나눠 담는다. 각 조각의 크기도 매번 다르다
  (같은 12296바이트짜리 패킷도 어떤 때는 frag가 2개, 어떤 때는 3개로
  나뉘고, 크기 분배도 매번 달라짐 — 게스트 내부 버퍼 상태에 좌우됨).

  게스트 커널 모듈은 dmesg에 이렇게 로그를 남긴다:

    frag[0]: compound_GPA=0x142700000  off=46      size=8976
    frag[1]: compound_GPA=0x142700000  off=9262     size=3320

  이건 "frag[0]은 compound_GPA+46 위치에서 시작해서 8976바이트짜리다"라는 뜻.

  우리가 하는 일 (모든 frag, 모든 후보 페이지를 다 모음):
    각 frag를 순서대로 뒤지면서, "이 frag 안에 4096바이트가 통째로
    들어가는 위치"를 전부 찾는다 (frag 하나에 clean 페이지가 여러 개
    있을 수도 있음 — 첫 번째 것만 쓰지 않고 전부 후보 목록에 모아둠).
    size가 4096바이트보다 작은 frag는 애초에 불가능하다(작은 상자엔
    큰 페이지가 안 들어감). 이렇게 후보를 여러 개 모아두면, 뒤에서
    설명할 정렬/충돌 회피 단계에서 선택지가 많아져 훨씬 유리하다.

  주의할 점: frag[0]의 맨 앞부분은 ICMP 헤더(8바이트) + byte_shift만큼의
  0x00 패딩이 섞여 있어서 순수 토큰 데이터가 아니다. 그래서 frag[0]에서
  "우리 토큰 데이터가 진짜로 시작하는 위치"는 (frag 시작 + 8바이트 +
  byte_shift) 부터다. frag[1] 이후는 헤더가 없으므로 그대로 시작.

────────────────────────────────────────────────────────────────────────────────
4. 8바이트 정렬 문제 (byte_shift)
────────────────────────────────────────────────────────────────────────────────

  실제 인디케이션 토큰이 메모리에 있는 위치는 항상 8의 배수 오프셋이다
  (토큰 하나가 8바이트 int64이고, 배열 시작 주소도 8-정렬이기 때문).

  그런데 우리가 딕셔너리에 등록하는 위치("이 페이지의 몇 번째 바이트부터
  깨끗한 토큰 사이클이 시작하는가", 이를 actual_landing이라 부름)가
  자연 상태로는 8의 배수가 아닌 값(예: 6, 14, 22...)으로 나올 수 있다.
  이러면 등록된 딕셔너리 항목이 실제 조회 위치(항상 8의 배수)와 절대
  만날 수 없어서 완전히 무용지물이 된다.

  원인: 게스트가 우리 패킷 데이터를 메모리에 놓는 시작 지점 자체가
  8의 배수가 아닌 어떤 나머지(예: mod 8 = 6)만큼 어긋나 있을 수 있다.

  해결: byte_shift라는 보정값(처음엔 0~7바이트, 충돌 회피 때문에 나중엔
  더 커질 수 있음)을 우리 페이로드 맨 앞에 0x00으로 끼워 넣는다. 이
  패딩 길이를 늘리면 "진짜 토큰 데이터가 시작하는 지점"이 그만큼 뒤로
  밀리기 때문에, 결과적으로 actual_landing 값을 조정할 수 있다.

    landing % 8 != 0 이면
      → byte_shift를 (8 - landing%8)만큼 늘려서 재전송
      → 다시 측정해서 8의 배수가 나올 때까지 반복

  주의: byte_shift를 얼마나 바꾸면 landing이 정확히 얼마나 움직일지는
  "예측 가능"하지 않다는 게 실측으로 확인됐다 (아래 6장 참고). 그래서
  byte_shift는 "정밀 조준"이 아니라 "재시도를 위한 손잡이"로만 쓴다 —
  바꿔서 다시 보내보고, 이번엔 어떻게 나오는지 관찰하는 식.

  비유: 컨베이어 벨트에 물건이 어디 떨어질지는 내가 못 정하지만,
  물건 앞에 완충재를 얼마나 붙일지는 내가 정할 수 있다. 완충재
  길이를 조절하면 "진짜 물건"이 벨트의 원하는 위치(8의 배수)에
  오도록 맞출 수 있다. 다만 정확히 몇 mm 밀어야 원하는 자리에
  떨어질지는 예측이 안 되므로, 몇 번 다시 던져보는 수밖에 없다.

────────────────────────────────────────────────────────────────────────────────
5. 왜 회전(rotation)이 필요한가 — ABC/BCA/CAB (2토큰도 예외 없음)
────────────────────────────────────────────────────────────────────────────────

  토큰이 N개짜리 라벨(예: "Short of breath" = [A, B, C], 각 8바이트)이라고
  하자. 실제 인디케이션에서 이 토큰들이 메모리 어디에 나타날지는 우리가
  모른다 — 페이지 안에서 8바이트 단위로 0, 8, 16, ... 어느 오프셋에서
  시작하든 나올 수 있다. N*8바이트 주기로 보면 가능한 시작 오프셋(잔차,
  residue)은 정확히 N가지 (예: 3토큰이면 0, 8, 16 mod 24).

  그런데 우리가 딕셔너리에 저장한 페이지 하나는 "ABC" 순서로 반복되는
  패턴이라서, 이 페이지 안에서 항상 "A로 시작하는 위치"만 깨끗한 3토큰
  경계다. 만약 실제 인디케이션에서 토큰들이 mod 24 기준으로 offset=8에서
  시작한다면(= B가 먼저 나옴), 우리가 가진 "A로 시작하는" 사전으로는
  절대 비교가 안 맞는다.

  그래서 순서를 바꾼 페이로드를 추가로 보낸다:
    rotation 0: A B C A B C ... (원래 순서)
    rotation 1: B C A B C A ... (한 칸씩 회전)
    rotation 2: C A B C A B ...

  이 N개를 각각 빌드해서 딕셔너리에 저장해두면, 실제 인디케이션이
  residue 0, 8, ..., (N-1)*8 중 어디서 시작하든 그 중 하나와는 반드시
  정확히 들어맞는다.

  2토큰 라벨도 예외 없이 이 방식을 그대로 쓴다 (rotation 0: [A,B],
  rotation 1: [B,A]) — 각 rotation이 "자기 자신의" landing=0(8의 배수
  정렬)만 잘 잡으면, rotation 1([B,A])이 자기 landing을 잘 잡는 것 자체가
  원본 [A,B] 순서를 residue 8에서 검증 가능하게 만들어준다. (참고:
  16바이트 span에서 offset%16==8로 "그 자리를 직접" 노리면 clean AES
  블록이 0개라 비교가 안 되지만, 그건 여기서 문제가 안 된다 — rotation 1은
  자기 자신의 landing==0을 노리는 것이지 landing==8을 노리는 게 아니기
  때문이다.) 예전엔 "2토큰은 rotation 1이 쓸모없다"고 착각해서 residue 8을
  포기했었는데, 이건 잘못된 가정이었고 지금은 고쳐졌다.

────────────────────────────────────────────────────────────────────────────────
6. 회전끼리 우연히 겹치는 문제 (collision)
────────────────────────────────────────────────────────────────────────────────

  각 회전이 "어느 residue를 커버하는가"는 그 회전을 보낼 때 실제로
  측정된 actual_landing 값에 따라 결정된다:

    reg_start = (actual_landing - rotation_번호 * 8) % L

  actual_landing이 회전마다 항상 똑같이(또는 예측 가능하게) 나온다면
  이 계산이 자동으로 서로 다른 N개의 residue를 깔끔하게 나눠 커버한다.
  하지만 실측 결과 게스트 쪽 배치 상태는 회전마다, 심지어 같은 byte_shift로
  재전송해도 예측과 다르게 나올 수 있다 (byte_shift를 정확히 +16 늘렸는데
  landing이 전혀 안 바뀌는 사례도 관측됨). 그래서 두 회전이 우연히 같은
  residue를 등록해버려서 다른 residue 하나가 완전히 비어버리는 일이 생긴다
  — 이게 collision.

  해결 (정밀 조준 대신 "여러 후보 + 재시도"):
    라벨 하나를 빌드하는 동안 "이미 커버한 residue 집합"(covered_residues)을
    계속 추적한다. 한 번 송신하면 3장에서 설명한 대로 여러 clean 페이지
    후보가 나올 수 있는데, 그 중:
      1순위: 8의 배수로 정렬됐고(aligned) AND 아직 안 커버된 residue를
             주는 후보 → 있으면 바로 그걸 채택 (재전송 불필요, 한 번에 끝)
      2순위: 정렬된 후보는 있지만 전부 이미 커버된 residue뿐이면(collision)
             → byte_shift를 +8만큼 늘려서 재전송 (정확한 delta 계산이
               아니라 그냥 조금 밀어서 다시 찔러보는 것 — 위 4장에서
               설명했듯 정밀 조준이 안 통하기 때문)
    이걸 최대 40번까지 반복한다. 한 번 보낼 때 여러 후보를 동시에 얻기
    때문에(3장), 재시도 한 번으로 여러 조합을 검사하게 되어 실제로는
    꽤 빨리 수렴한다.

  라벨 하나의 모든 회전이 끝나면 마지막으로 "0, 8, 16, ... 전부 다
  커버됐는지" 검증하고, 빠진 게 있으면 경고 로그(incomplete coverage)를
  남긴다.

────────────────────────────────────────────────────────────────────────────────
7. 전체 흐름 한 장으로 정리
────────────────────────────────────────────────────────────────────────────────

  라벨 하나(예: "Short of breath", 3토큰, L=24)를 빌드하는 과정:

    covered_residues = {}   (이 라벨에서 이미 커버된 residue 집합)

    for 회전 in [ABC, BCA, CAB]:
        이미 achievable_residues(={0,8,16}) 전부 커버됐으면 바로 스킵
        (남은 회전을 보내봤자 새 residue가 안 나올 게 뻔하므로 헛수고 방지)

        while 아직 성공 못함, 최대 40번:
            1. byte_shift만큼 0x00 패딩 + 회전된 토큰 패턴 12288B 반복
               → ICMP 패킷 하나로 전송 (drain_count 기준으로 주기적으로
                 게스트 수신 버퍼 flush)
            2. 게스트 dmesg에서 frag[0], frag[1], ... 각각의
               compound_GPA/off/size 읽어옴
            3. 모든 frag의 모든 "완전히 깨끗한 4096B 페이지" 후보를
               전부 모음 (candidates 리스트)
            4. 후보가 하나도 없으면 이 시도는 실패 → 스킵(드묾)
            5. 후보 중 actual_landing % 8 == 0 인 것만 추림(aligned)
               → 하나도 없으면 byte_shift 보정 후 재시도 [align-fix]
            6. aligned 후보 중 아직 안 커버된 residue를 주는 게 있으면
               → 바로 채택, break (성공)
            7. 전부 이미 커버된 residue뿐이면(collision)
               → byte_shift += 8 하고 재전송 [collision]

        성공하면: 그 페이지를 read_gpa로 덤프해서 저장하고,
        reg_start, reg_start+L, reg_start+2L, ... (페이지 끝까지)
        위치에 이 라벨의 dict 항목으로 등록. covered_residues에 추가.

    라벨의 모든 회전이 끝나면 achievable_residues가 전부 커버됐는지
    최종 검증, 빠지면 경고 로그.

  이걸 28개 라벨(2토큰도 포함해 전부 N개 회전 — 총 phase 수는 라벨별
  토큰 수의 합) 전부에 대해 반복하면 빌드 완료. 결과는 dict_cache.json
  (오프셋 → 라벨별 GPA/파일 경로)과 dict_pages/*.out(각 페이지의 실제
  암호문 덤프) 두 가지.

────────────────────────────────────────────────────────────────────────────────
8. 빌드 결과를 실제로 어떻게 쓰는가 (run_all과의 연결)
────────────────────────────────────────────────────────────────────────────────

  나중에 run_all이 실제 추론을 관찰할 때:
    1. 게스트에서 base_gpa, N(image_pad 수), N_indication_tokens
       (indication의 정확한 토큰 길이 — 검증용 샘플이라 게스트가
       알려줄 수 있음)을 받음
    2. indication이 시작하는 정확한 위치(tok_start = HEADER_CONST + N)
       계산, 거기서부터 N_indication_tokens개 위치만 정확히 스캔
       (짧으면 짧은 대로, 길면 긴 대로 — 매번 다른 크기로 대충 짐작하지 않음)
    3. 각 위치의 오프셋(mod 4096)으로 dict_cache.json을 조회, 라벨은
       짧은 토큰 개수 순서(_LABEL_ORDER)로 검사 — 짧은 라벨이 실제로
       거기 있으면 그게 먼저 매칭돼서, 그걸 포함하는 긴 라벨의 위험한
       부분매칭(정렬 문제로 앞/뒤 토큰이 스킵되는 경우)까지 갈 필요가
       없어짐
    4. 조회된 각 라벨 후보에 대해, 그 페이지를 swap-back으로 읽어서
       dict_pages/*.out에 저장된 ciphertext와 AES 블록 단위로 비교
    5. 완전히 일치하면 그 라벨이 실제로 그 위치에 있었다는 뜻

  즉 빌드 단계는 "비교 기준이 되는 사전"을 만드는 과정이고, run_all은
  그 사전을 실제 게스트 메모리와 대조하는 과정이다.

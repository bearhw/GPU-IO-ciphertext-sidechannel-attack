────────────────────────────────────────────────────────────────────────────────
0. 전체 목적
────────────────────────────────────────────────────────────────────────────────

AMD SEV-SNP으로 암호화된 게스트 VM에서 LLM(의료 VLM) 추론을 실행할 때,
호스트에서 게스트 메모리를 복호화하지 않고도 indication 토큰을 추론하는
사이드채널 공격 PoC (Dictionary-based ciphertext comparison).

핵심 원리:
  AES-XEX 암호화에서 동일한 plaintext + 동일한 GPA(Guest Physical Address) =
  항상 동일한 ciphertext. 따라서 미리 알려진 토큰을 알려진 GPA에서 캡처한
  ciphertext와, 추론 중 indication 토큰이 위치한 GPA의 ciphertext를 비교하면
  어떤 토큰인지 식별 가능.

3. HEADER_CONST와 indication_gpa 계산
────────────────────────────────────────────────────────────────────────────────

  게스트에서 LLM 추론 시, input_ids 배열이 메모리에 배치될 때:

    indication_gpa = base_gpa + tok_start * 8

  indication_page_gpa = indication_gpa & ~0xFFF   (4KB 페이지 정렬)
  token_offset        = indication_gpa & 0xFFF     (페이지 내 오프셋)

────────────────────────────────────────────────────────────────────────────────
4. Phase 0: 딕셔너리 빌드 (--build)
────────────────────────────────────────────────────────────────────────────────

목표: 모든 token_idx(0~3) × 모든 가능한 page offset 조합에 대해
      ciphertext를 미리 캡처해 dict_cache.json에 저장.

4-1. 항상 새로 빌드
  --build 실행 시 기존 dict_cache.json과 dict_pages/*.out 파일을 전부 삭제.
  중간 resume 없음 — 처음부터 새로 시작.

4-2. Phase 기반 최적화
  각 token_idx는 token_len(L) 바이트 길이의 payload를 가짐.
  L = len(token_ids) * 8    (token_idx=0,2: L=16,  token_idx=1,3: L=32)
  n_phases = L // 8          (token_idx=0,2: 2 phases,  token_idx=1,3: 4 phases)

  phase p는 target_landing = p*8 위치에 첫 토큰 바이트가 오는 경우를 캡처.
  payload가 L바이트 간격으로 반복되므로, 한 번의 dump로
    p*8, p*8+L, p*8+2L, ... 위치를 모두 커버.

  전체 phase 수: 143개 (TOKEN_LABELS 35개 기준, 상세 테이블은 §20 참고)
  send 횟수: 각 token_idx의 첫 phase에서 probe 4회+aligned 1회, 이후 phase는 carry-forward 1회
    → 35×5 + 108×1 = 283회 (착지 재시도 없는 경우)
  [구 TOKEN_LABELS 10개: 33 phases, 구 2-probe 방식: ~99회]

4-3. 각 phase 처리 흐름
  a. 링 상태 carry-forward (첫 phase 제외):
       이전 phase의 actual_frag_p1과 delta가 있으면 probe 생략.
       expected_frag = (frag_p1_last - delta) % 4096  (1회 aligned send만 필요)

  b. probe 없을 때: 소형 probe × 2 (prefix=0):
       acquire_token_gpa(token_idx, prefix=0) × 2
       → frag_p1_a, frag_p1_b 획득
       delta_small = (frag_p1_a - frag_p1_b) % 4096
       expected_frag_rough = (frag_p1_b - delta_small) % 4096

     이유: delta = ring advance per packet ≈ 보낸 패킷 크기 % 4096.
     prefix=0(소형)와 aligned send(대형)의 패킷 크기가 다르면 delta도 달라
     착지 예측이 빗나간다 → 아래 대형 probe로 정확한 delta 측정.

  c. 대형 probe × 2 (prefix = target_landing + expected_frag_rough):
       acquire_token_gpa(token_idx, prefix=_large_pfx) × 2
       → frag_p1_c, frag_p1_d 획득 (aligned send과 동일한 패킷 크기)
       delta_large = (frag_p1_c - frag_p1_d) % 4096
       expected_frag = (frag_p1_d - delta_large) % 4096
       prefix = target_landing + expected_frag

  d. 정렬 send:
       acquire_token_gpa(token_idx, prefix=prefix)
       → dict_gpa, actual_frag_p1 획득
       actual_landing = (prefix - actual_frag_p1) % 4096
       → target_landing과 정확히 일치해야 OK

  e. 착지 재시도 (최대 _MAX_LANDING_TRIES=20회):
       actual_landing ≠ target_landing이면:
         error = (actual_landing - target_landing) % 4096
         delta_corrected = (delta - error) % 4096
         (fallback: 대형 probe 실패해서 소형 delta 사용 중일 때)
       5회마다: re-probe (소형 2 + 대형 2 = 4패킷)
       wrong-landing 항목은 캐시에 보존 (해당 offset의 유효한 ciphertext).

  f. 4KB 페이지 덤프:
       read_gpa.py로 dict_gpa의 ciphertext 저장
       → dict_pages/t{token_idx}_p{phase}.out

  g. 딕셔너리 등록:
       actual_landing + k*L (k=0,1,2,...) 위치의 off_key들에 대해
       cache[off_key][str(token_idx)] = {gpa, cp_file, landing_ok} 저장

  h. token_idx 완료 후 dict_cache.json 저장 (진행 상황 보존)

4-4. acquire_token_gpa 내부 동작
  - 게스트 dmesg 초기화 (ssh "sudo dmesg -C")
  - host에서 ICMP 패킷 전송 (send_tokens.py)
  - 게스트 dmesg에서 "sub-page[N] GPA=0x..." 패턴 파싱 → GPA 획득
  - "frag[0] ... off=NNN" 패턴 파싱 → frag_p1 계산
  - 5회 실패 시 RuntimeError → 호출측에서 phase 스킵

4-5. drain 버퍼
  DRAIN_EVERY(=16)번 phase마다 게스트 ICMP 수신 버퍼 강제 flush.
  → 쌓인 패킷이 다음 측정에 영향 미치지 않도록.

  probe 또는 aligned send가 5회 모두 실패하면 즉시 drain 후 phase 스킵.
  → 버퍼 적체로 인한 연쇄 실패 방지.

────────────────────────────────────────────────────────────────────────────────
5. do_swap_read: 원자적 swap-back 읽기
────────────────────────────────────────────────────────────────────────────────

compare와 calibrate 모두에서 사용하는 비파괴적 페이지 읽기:

  1. swap_pages_tool --swap-back 호출:
       forward swap(dict_gfn ↔ src_gfn)
       → dict_gfn의 물리 프레임에 src 데이터가 배치됨 (AES-XEX: dict_gfn의 tweak 적용)
       → 커널 버퍼로 ciphertext 복사
       → backward swap (원래 상태 복원)
     → 모두 svm_vcpu_run() 이전 한 번의 atomic 동작으로 실행
     → 게스트는 swap 상태를 전혀 볼 수 없음 (SEV_TERM 없음)

  2. /dev/kvm에 KVM_READ_PAGE_DUMP ioctl:
       커널 버퍼의 4096바이트를 호스트 userspace로 복사

  3. xp /512gx 형식으로 포맷해 .out 파일로 저장

  KVM_READ_PAGE_DUMP = _IOR(0xAE, 0x2b, 4096) = 0x80100AE2b (계산값)

6. Phase 1a: HEADER_CONST 자동 교정 (--calibrate)
────────────────────────────────────────────────────────────────────────────────

  HEADER_CONST의 정확한 값을 모르거나 검증하려 할 때 사용.

  흐름:
    1. 게스트에서 --gpa-only로 base_gpa, N 획득 (_acquire_gpa_raw)
    2. h를 CAL_H_MIN(30)부터 CAL_H_MAX(60)까지 1씩 증가하며 sweep:
         tok_start    = h + N
         token_offset = (base_gpa + tok_start*8) & 0xFFF
         src_gpa      = (base_gpa + tok_start*8) & ~0xFFF

         - token_offset이 dict에 없으면 skip
         - dict에 있는 각 token_idx에 대해 do_swap_read 실행:
             cal_h{h}_t{token_idx}.out 저장
         - verify.py로 cp(딕셔너리 덤프) vs post(방금 읽은 덤프) 비교
         - "Result: MATCH ✓"이면 h 반환 (sweep 중단)

    3. 매칭되는 h가 없으면 None 반환 → 범위 확장 또는 딕셔너리 재빌드 필요

  참고: 게스트 프로세스는 GPA 획득 후 --gpa-only 모드로 대기 중이며,
        calibration이 끝나면 프로세스를 종료함.

  [2026-07-29 추가] AES 정렬 문제와 retry 로직:
    - calibrate 실패 원인: token_offset % 16 == 8 일 때
      2-token(16B) 레이블은 clean AES 블록이 0개 → verify 항상 실패.
      4-token(32B) 레이블은 16B이므로 clean 블록 1개 존재 → 비교 가능.

    - CAL_MAX_RETRIES = 3 (재시도 횟수)
      각 시도마다 게스트에서 새 base_gpa를 획득한다.
      base_gpa는 실행마다 달라지므로 token_offset도 달라짐 →
      mod16=8 고착 확률이 약 50%이므로 3번 안에 좋은 정렬을 얻을 확률 ≈ 87%.

    - 2026-07-29 실측: calibrate-index=28로 처음 실행했을 때
      h=43 (구 HEADER_CONST)으로도 No match 발생.
      retry로 새 base_gpa 획득 후 h=55에서 MATCH → HEADER_CONST=55 확정.

9. compare_with_dict 내부 동작
────────────────────────────────────────────────────────────────────────────────

  token_offset → off_key(hex) → cache[off_key] 조회

  각 token_idx(0~3)에 대해:
    1. cache에서 dict_gpa, cp_file(딕셔너리 덤프 경로) 조회
    2. do_swap_read(swap_tool, dict_gpa, indication_page_gpa, post_path)
         → indication 페이지를 dict_gpa의 AES-XEX tweak으로 읽기
         → post_path(post_off{offset}_t{token_idx}.out)에 저장
    3. verify.py로 비교:
         --cp:           딕셔너리 단계에서 캡처한 ciphertext (토큰 plaintext가 있을 때)
         --post:         방금 do_swap_read로 읽은 indication 페이지 ciphertext
         --token-offset: 페이지 내 토큰 오프셋
         --token-ids:    해당 token_idx의 int64 ID 목록
    4. "Result: MATCH ✓" → (token_idx, "MATCH") 반환 (즉시 중단)
    5. 모두 MISMATCH → (None, "MISMATCH") 반환

────────────────────────────────────────────────────────────────────────────────
10. verify.py 비교 로직
────────────────────────────────────────────────────────────────────────────────

  parse_dump(path): xp /512gx 형식 텍스트 → raw bytes (little-endian 64-bit pair)

  clean_aes_blocks(token_offset, token_len):
    토큰 바이트 범위 [token_offset, token_offset+token_len) 내에
    완전히 포함되는 16-byte AES 블록의 오프셋 목록 반환.
    경계에 걸치는 partial 블록은 제외 (주변 데이터가 달라서 비교 불가).

  cmd_verify:
    clean_aes_blocks 목록의 각 블록 위치에서 cp vs post 비교.

────────────────────────────────────────────────────────────────────────────────
16. HEADER_CONST · N 개념 및 --blind 모드
────────────────────────────────────────────────────────────────────────────────

16-1. 두 값이 왜 필요한가
──────────────────────────

  게스트에서 LLM 추론이 시작되면, input_ids 배열이 CPU 메모리에 다음 순서로 배치됨:

    [ 헤더 토큰 × HEADER_CONST ]
    [ <|image_pad|> 토큰 × N  ]
    [ indication 토큰          ]  ← 공격 목표

  호스트가 indication 토큰을 읽으려면 정확한 GPA가 필요:

    indication_gpa = base_gpa + (HEADER_CONST + N) × 8

  - base_gpa   : input_ids[0]의 GPA. 게스트 스크립트가 stdout으로 출력.
  - HEADER_CONST : 프롬프트 템플릿이 고정된 한 모든 샘플에서 동일한 상수.
                   현재 값: 43. --calibrate로 검증.
  - N          : 이미지 한 장당 삽입되는 <|image_pad|> 토큰 수.
                 이미지 해상도마다 달라짐 (관측 범위: 80~1178).

16-2. N은 어떻게 결정되나
──────────────────────────

  Qwen2-VL은 입력 이미지를 smart_resize()로 28의 배수 해상도로 조정한 뒤,
  14×14 픽셀 패치로 분할하고 4개씩 묶어 하나의 토큰으로 압축:

    resized_h, resized_w = smart_resize(orig_H, orig_W, factor=28)
    N = (resized_h // 14) × (resized_w // 14) // 4

  예시:
    원본 756×756  → N = 729
    원본 420×504  → N = 270
    원본 448×532  → N = 304

  N은 이미지 해상도가 같으면 항상 동일 → 게스트 없이 계산 가능
  (호스트가 게스트 디스크에서 DICOM 헤더를 읽어 H,W → N 계산).

16-3. 기존 방식의 한계
───────────────────────

  기존 --calibrate / --index 흐름:
    - 게스트 스크립트(single_inference_indication_gpa.py)가
      base_gpa 와 N 을 stdout으로 출력
    - 호스트가 SSH로 두 값을 파싱 → indication_gpa 계산

  한계: 게스트가 N을 직접 알려줘야 함 (게스트 협조 필요).

16-4. --blind 모드 동작 방식
──────────────────────────────

  핵심 관찰:
    HEADER_CONST ∈ [30, 60] (CAL_H_MIN~MAX)
    N            ∈ [80, 1180] (N_SWEEP_MIN~MAX, 관측 기반)
    → tok_start = HEADER_CONST + N ∈ [110, 1240]

  두 값을 개별로 sweep하는 게 아니라, 합(tok_start)만 sweep:
    - 후보 수: 1240 - 110 + 1 = 1131개 (2D 탐색 불필요)
    - 각 후보에서 indication_gpa 계산 → ciphertext 비교
    - MATCH → tok_start, indication_gpa, token_idx 동시 확정

  실행 흐름:
    1. 게스트에서 base_gpa만 파싱 (N 출력 전에 reader 스레드 중단)
    2. tok_start ∈ [110, 1240] 순서대로:
         ind_gpa      = base_gpa + tok_start × 8
         token_offset = ind_gpa & 0xFFF
         → cache에 없으면 skip
         → swap-back read + verify (조용히, log 출력 없음)
         → "Result: MATCH ✓" → 즉시 리턴
    3. MATCH: tok_start, indication_gpa, token_idx 확정
       MISMATCH 전체: verdict="MISMATCH" 저장

  성능:
    - base_gpa가 8-byte aligned이므로 token_offset은 항상 8의 배수
    - cache는 8의 배수 offset을 전부 커버 → 모든 tok_start가 cache hit
    - 최악 1131 × 4(token_idx) = 4524번 swap-back read ≈ 4.5초
    - MATCH는 보통 훨씬 일찍 발생

  [2026-07-29] 구 sweep_blind의 core dump 원인 및 새 구현:
    → §18 참고.

17. HEADER_CONST 안정성 및 올바른 값 (2026-07-29 확인)
────────────────────────────────────────────────────────────────────────────────

17-1. HEADER_CONST는 VM 세션마다 바뀌지 않는다
───────────────────────────────────────────────

  HEADER_CONST = 모델 토크나이저 + 시스템 프롬프트가 생성하는 고정 헤더 토큰 수.
  input_ids 배열 맨 앞에 항상 동일한 구조로 배치되는 토큰들:
    [bos] [system_header] [시스템 프롬프트 토큰들] [vision_start] [image_pad...] ...

  이 값이 변하려면 다음 중 하나가 바뀌어야 한다:
    - 모델 자체 (Qwen2-VL 가중치 교체)
    - 시스템 프롬프트 텍스트
    - 토크나이저 어휘/설정

  VM 재시작, QEMU 재실행, 이미지 교체는 영향 없음.
  → 한 번 calibrate하면 이후 모든 세션에서 동일한 값 사용 가능.

17-2. 올바른 값: HEADER_CONST = 43
───────────────────────────────────

  HEADER_CONST = 43 이 정확한 값이다.

  과거에 잘못된 calibration 결과(h=55)가 기록된 적 있었으나, 이는
  calibrate-index=28을 사용했기 때문이다. index=28의 indication은
  "Chest pain."(마침표 포함)으로, TOKEN_LABELS에 없는 샘플이다.
  해당 샘플은 prefix_tokens=20(Sex만 있는 짧은 메타데이터)으로,
  prefix_tokens=28인 주류 샘플과 HEADER_CONST가 다르다.
  → 엉뚱한 샘플로 calibrate하면 그 샘플에 맞는 h가 나올 뿐, 전체에 적용 불가.

  올바른 calibration 방법:
    - calibrate-index는 반드시 TOKEN_LABELS에 exact-match되는 샘플 사용
    - 권장 index: 13 ("Shortness of breath", 4-token, prefix_tokens=28)
    - sudo python3 orchestrate_v2.py --calibrate --calibrate-index 13

  현재 코드: HEADER_CONST: int | None = 43

17-3. AES 정렬 문제 (token_offset % 16 == 8)
─────────────────────────────────────────────

  AES-XEX는 16-byte 블록 단위로 암호화.
  토큰 바이트 범위가 16-byte 경계와 어떻게 겹치느냐에 따라 비교 가능 블록 수가 달라짐.

  2-token 레이블 (16B):
    - token_offset % 16 == 0: 정확히 1개의 clean AES 블록 → 비교 가능
    - token_offset % 16 == 8: 블록 2개에 걸침 → clean 블록 0개 → 비교 불가
    - token_offset % 16의 다른 값: partial → 비교 불가

  4-token 레이블 (32B):
    - 어떤 token_offset에서도 32B 범위 안에 16B 블록이 최소 1개 완전히 들어감
    - 최악(token_offset % 16 == 8): 첫 블록 일부 + 두 번째 16B 블록 완전히 포함
    → 항상 비교 가능 (clean AES 블록 ≥ 1)

  실전 의미:
    - calibrate 실패 원인의 상당수가 이 정렬 문제
    - token_offset % 16 == 8이면 4-token 레이블만 비교 가능
    - retry로 새 base_gpa를 받으면 token_offset이 달라질 확률 ~50%

18. --blind 모드 core dump 원인과 두 페이즈 재구현 (2026-07-29)
────────────────────────────────────────────────────────────────────────────────

18-1. 구 sweep_blind의 core dump 원인
──────────────────────────────────────

  구 구현: tok_start ∈ [CAL_H_MIN + N_SWEEP_MIN, CAL_H_MAX + N_SWEEP_MAX]
           = [110, 1240] 전체를 순서대로 sweep.

  문제:
    tok_start=1240 이면 byte_offset = 1240 × 8 = 9920B.
    4096B 경계를 3번 넘음 → 3개 물리 페이지 접근.

    input_ids 텐서의 실제 크기:
      N_image_pad × 8 + (헤더 + indication) × 8 ≈ N_actual × 8 바이트.
      N_actual=80 이면 텐서 크기 ≈ 1168B → 페이지 1개 안에 들어감.

    tok_start > (텐서 크기/8) 위치의 페이지는 input_ids 바깥 →
    PyTorch 내부 메모리 할당 (텐서 메타데이터, 다른 텐서 등)에 속함.

    그 페이지를 swap-back으로 교체하면 게스트 메모리 구조가 망가짐 →
    SEV_TERM / KVM_SYSTEM_EVENT_SEV_TERM → 게스트 core dump.

18-2. 구현: Two-Phase Blind Sweep (이진 탐색, 2026-08-03)
──────────────────────────────────────────────────────────

  input_ids 배열 구조:
    [0..FIRST_PAD_POS-1]       : 고정 헤더 토큰 (15개)
    [FIRST_PAD_POS..+N-1]      : <|image_pad|> × N
    [FIRST_PAD_POS+N..+POST-1] : vision_end 등 POST_SCAN 토큰 (20~60개)
    [FIRST_PAD_POS+N+POST..]   : indication 토큰  ← 공격 목표
    (HEADER_CONST = FIRST_PAD_POS + POST_SCAN_typical = 15 + 28 = 43)

  Phase 1 — 이진 탐색으로 N 추정 (_binary_search_ipad_end):
    탐색 대상: image_pad×4 sentinel(token_idx=34)이 True인 마지막 tok_start.
    image_pad가 [FIRST_PAD_POS, FIRST_PAD_POS+N-1]에 있으므로
    _check_tok_is_image_pad(p) = True iff p ≤ FIRST_PAD_POS+N-4 (or ~N-3, mod16에 따라)

    탐색 범위:
      lo = FIRST_PAD_POS + N_SWEEP_MIN - 4 = 41
      hi = FIRST_PAD_POS + N_SWEEP_MAX - 3 = 1212
    swap 횟수: ⌈log2(1172)⌉ ≈ 11회 (구 선형: 최대 1101회, ~100× 개선)

    last_true 반환 → N_est = last_true - FIRST_PAD_POS + 4

  Phase 2 — indication 매칭:
    tok_start ∈ [FIRST_PAD_POS + N_est + POST_SCAN_MIN - 1,
                 FIRST_PAD_POS + N_est + POST_SCAN_MAX + 1]
    = N_est + 14 ~ N_est + 76  (≈63 steps)
    TOKEN_LABELS 0~33 (sentinel 제외) 전체와 비교.
    ≤63 tok_start × 34 token_idx = 최대 2142회 swap
    (실측: 페이지 공유로 실제 swap 수 훨씬 적음)

    linear fallback: binary search 실패 시
      tok_p2_min = FIRST_PAD_POS + POST_SCAN_MIN
      tok_p2_max = FIRST_PAD_POS + N_SWEEP_MAX + POST_SCAN_MAX  (전체 범위)

  헬퍼 함수:
    _swap_read_raw(swap_tool, dict_gpa, ind_page_gpa) → bytes | None
      swap-back + KVM_READ_PAGE_DUMP를 묶어 raw bytes 반환.
    _check_tok_is_image_pad(base_gpa, tok_start, cache, swap_tool) → True/False/None
      None = swap-self (broken range) → binary search에서 hi = mid-1로 처리.

v3는 v2의 --blind 로직을 run_all()에 통합한 버전. 파일: orchestrate_v3.py

20-1. TOKEN_LABELS 토큰 ID 검증 완료
──────────────────────────────────────

  guest에서 실제 Qwen2-VL tokenizer(Qwen/Qwen2-VL-2B-Instruct, HF hub cache)를
  돌려 TOKEN_LABELS의 모든 28개 라벨 토큰 ID를 재확인함.

    ssh -p 7777 ubuntu@localhost
    conda activate vlm
    python3 -c "from transformers import AutoTokenizer; \
      tok = AutoTokenizer.from_pretrained('Qwen/Qwen2-VL-2B-Instruct'); \
      print(tok.encode(' <label>', add_special_tokens=False))"

  결과: 현재 orchestrate_v3.py의 TOKEN_LABELS 전부 정확함 (오타/오매핑 없음).
  → FP(false positive)의 원인은 토큰 ID 오류가 아니었음. 아래 20-2 참고.

20-2. run_all FP의 진짜 원인: stale N_meta 기반 스캔
──────────────────────────────────────────────────────

  기존 run_all():
    base_gpa, _, proc = _acquire_gpa_raw(index, base_only=True)   # N 버림
    tok_start, ind_gpa, token_idx = sweep_blind(base_gpa, cache, swap_tool,
                                                 N=sample.get("N"))  # stale N_meta 사용

  filtered_samples.json의 N 필드(N_meta)는 오래된 값이라 실제 추론 시의
  N_actual과 다를 수 있음 (delta = N_meta - N_actual ∈ [-30, +9], 62% 샘플에서 stale).
  N_meta가 부정확하면 sweep_blind의 42-step 스캔 창이 실제 indication 위치와
  어긋나거나, 짧은 indication에서 스캔 상한이 텐서 끝을 넘어가 엉뚱한 위치에서
  라벨이 우연히 매칭되는 FP가 발생함 (예: index=322 "Short of breath,CHF" →
  "Chest pain"으로 오매칭, index=303 "Chest pain,cough,congestion" →
  "Shortness of breath"로 오매칭).

  수정:
    base_gpa, N_actual, proc = _acquire_gpa_raw(index, base_only=False)  # N 획득
    tok_start, ind_gpa, token_idx, N_est = sweep_blind(base_gpa, cache, swap_tool,
                                                        N=N_actual, exact=True)

  exact=True 경로에서 sweep_blind는 스캔 없이 단일 위치만 확인:
    tok_start_exact = HEADER_CONST + N_actual
    tok_p2_min = tok_p2_max = tok_start_exact

  단, base_only=False는 guest가 모델 forward pass를 끝내고 stdout에
  "N_image_pad: X"를 출력할 때까지 기다려야 하므로 느림 (모델 추론 완료 필요).
  → 20-3의 --blind 모드가 이 문제의 대안.

20-3. --blind CLI 플래그: binary search로 N 없이 진행
────────────────────────────────────────────────────────

  신규 인수: --blind (run_all과 함께 사용)

    sudo python3 orchestrate_v3.py --run-all --blind --swap-tool ./swap_pages_tool

  동작:
    base_gpa, _, proc = _acquire_gpa_raw(index, base_only=True)  # base_gpa만, N 안 기다림
    tok_start, ind_gpa, token_idx, N_est = sweep_blind(base_gpa, cache, swap_tool)  # N=None

  sweep_blind(N=None)일 때 Phase 1 이진탐색(_binary_search_ipad_end)이 실행됨.
  guest가 N을 stdout에 출력하기 전에 base_gpa만 받고 바로 진행 가능
  → 모델 forward pass 완료를 기다릴 필요 없음 (base_only=True가 더 빠름).

  결과 CSV 분리:
    RESULTS_CSV       = run_all_v3.csv         (--blind 없을 때, exact 모드)
    RESULTS_CSV_BLIND = run_all_v3_blind.csv   (--blind 지정 시)

  verdict 3종류 (CSV의 "verdict" 컬럼):
    MATCH         : 라벨 매칭 성공
    NO_MATCH      : N 확정(exact 또는 binary search) 후 스캔했지만 라벨 불일치
    BSEARCH_FAIL  : binary search 자체가 N을 못 찾음 (last_true=None)

  N_est 컬럼 추가: binary search가 추정한 N (또는 exact 모드의 N_actual).
  BSEARCH_FAIL일 때는 N_est도 빈 값 — 실패 유형 구분 가능.

20-4. binary search (_binary_search_ipad_end) 동작 원리
──────────────────────────────────────────────────────────

  전제: image_pad 토큰은 전부 동일 ID(151655). 같은 GPA로 swap하면
  AES-XEX ciphertext도 동일하므로, dict의 "image_pad×4" sentinel과
  비교해 "이 위치가 image_pad 구간 안인가"를 판별 가능.

  단조성:
    position:  15  16  17 ... N+14 | N+15  N+16 ...
    token:     PAD PAD PAD... PAD  | END   TPL  ...
    AES match:  T   T   T  ...  T  |  F     F  ...

  → TRUE 구간이 앞쪽에 몰려 있으므로 이분탐색으로 마지막 TRUE 위치
    (last_true)를 log2(범위) 회 만에 찾을 수 있음.

  탐색 범위 (2026-08-05 수정):
    이전: lo = FIRST_PAD_POS + N_SWEEP_MIN - 4 = 41   (N≥30 가정 — 불필요한 제약)
    수정: lo = FIRST_PAD_POS = 15                      (image_pad 시작 위치, 고정값)
          hi = FIRST_PAD_POS + N_SWEEP_MAX = 1215

  mid = (lo+hi)//2 위치에서 _check_tok_is_image_pad 호출 →
    True  → last_true=mid, lo=mid+1
    False/None → hi=mid-1
  약 11회 만에 last_true 확정 → N_est = last_true - FIRST_PAD_POS + 4

20-5. swap 실패가 실제로 발생하는 경우
──────────────────────────────────────

  dict 커버리지는 512/512 offset 전부 확보되어 있어 "dict에 없어서 실패"하는
  경우는 없음. 실제 swap 실패(BSEARCH_FAIL)가 발생할 수 있는 유일한 시나리오:

    guest 프로세스가 sweep_blind 도중 종료되어, input_ids 텐서가 있던 물리
    페이지가 free된 뒤 다른 용도(다음 네트워크 패킷 버퍼, 다른 텐서 등)로
    재사용되는 경우. 이 경우 swap으로 읽은 내용이 더 이상 indication
    토큰이 아니게 됨.

  방지책 (기존에 이미 구현되어 있음):
    run_all()은 _acquire_gpa_raw가 반환한 guest ssh subprocess(proc)를
    sweep_blind가 완전히 끝날 때까지 kill하지 않고 살려둠 → guest 프로세스가
    --gpa-only 모드로 대기 중이므로 텐서가 free되지 않음. sweep 종료 후에만
    proc.kill() 호출.

21. 요약: 실행 방법 (v3)

  # 딕셔너리 빌드

  → run_all_v3_blind.csv
